Dashboard Generator

Every schedule sensor (Settings → Devices & Services → FLARE Schedules → Add schedule sensor) gets the same shape of dashboard section: the curve, a phase override, the five schedule times, the eight curve values, and the eight transition minutes. Typing the slug once below builds the whole thing instead of hand-editing 25 entity IDs.

Just want the chart? On Home Assistant 2026.6 and newer you don't need this page for that — add a card, switch to the By entity tab, pick your schedule sensor, and FLARE Curve is offered under Community with a live preview, already sized to fill its section. The generator below is for the rest: the picker only ever suggests the one card, not the 24 controls that go around it.

Paste into a sections view's raw YAML editor

column_span: 4 on the outer grid and grid_options: {columns: full} on the curve card aren't decorative — a card inside a sections view doesn't inherit its section's full width just because the section itself is full-width, so both are needed for the curve to actually span the section instead of rendering at roughly a third of it.

The Curve and Transitions groups are each a nested grid card at columns: 2, so a row is always exactly one phase — brightness beside colour, Morning down to Night — and reading down a column gives you one channel across the whole day. That has to be the grid card's own columns, not per-tile grid_options: the latter counts against the section's grid, which is 12 columns times its column_span, so a fixed per-tile value lands on a different number of tiles per row as the window changes width. Fine where nothing depends on which cards are adjacent — the Override pair and the five schedule times still use it — and not fine for a layout that is entirely about which two tiles sit together. The nested grid needs its own grid_options: {columns: full} for the same reason the curve card does.

The four brightness values are tiles carrying the numeric-input feature (style: slider) — drag to set the value directly from the dashboard, no need to open anything. The slider's own range comes from the entity itself (0–255), not from anything typed into this generator, so it can never drift out of sync with what the entity actually accepts. The four colour-temperature values get FLARE's own slider instead — see below. Every feature sits inline — on the same row as the tile's name rather than stacked under it — so a slider is half the height it would otherwise be.

Phase and Sticky are directly actionable the same way — a select-options dropdown and a toggle respectively, both inline. The five schedule times deliberately aren't: a time entity has no inline-editable feature, so tapping the tile to open the time picker is the best available option.

The eight transition tiles carry no feature at all, which is also deliberate. They run 0–1440 minutes — a whole day, so that "always be transitioning" is expressible rather than an error — while any value you'd actually set is under an hour. A slider would spend about 96% of its travel out of reach and a single pixel would be worth several minutes. The numeric-input feature takes no min/max of its own (its whole config is {type, style}), so there's nothing to narrow, and style: buttons steps by the entity's step of 1, i.e. 45 taps to reach 45 minutes. So a transition tile falls through to its more-info dialog — which FLARE already sets to mode: box, a number you type rather than a second slider. For a duration that's the right interaction anyway, and it halves the group's height.

Reading the section at a glance

Twenty-five near-identical controls is a lot to scan, so the section is colour-coded along one axis and icon-coded along the other:

  • Colour is the phase. Morning is blue, Day yellow, Evening orange, Night indigo — the same colour wherever that phase appears, in the Schedule group, the Curve group and Transitions alike. The palette tracks the colour temperature the curve actually reaches in each phase rather than the time of day: Morning ramps to the coldest, bluest light of the day, and each phase after it is warmer than the last. That reads backwards against a sunrise/sunset mental model, and right against the curve drawn directly above it.
  • Icon is the channel. Brightness controls carry mdi:brightness-6 and colour-temperature controls mdi:temperature-kelvin, whichever phase they belong to. Transitions are durations rather than levels, so they all take mdi:timer-sand instead — the two groups otherwise use identical tile names.

A tile's color reaches its slider, not just its icon: the tile card publishes --feature-color from its own colour, so the brightness fill you drag is the phase colour too. That only applies while the entity counts as "active", which for a number is always — so a transition left at 0 still shows its phase colour rather than greying out. Sticky is the deliberate exception: it's a switch, so it greys itself out when off, which is exactly the right signal for an override that isn't engaged.

The colour-temperature slider

The four colour-temperature controls use FLARE Colour temperature (type: custom:flare-kelvin-feature) rather than the built-in slider. It is the built-in slider — the same ha-control-slider element, given the same settings, so the handle, the rounded fill, the tooltip and the keyboard behaviour are all Home Assistant's own. The only difference is that its fill is painted in the colour temperature it's set to, and changes colour as you drag it.

It exists because --feature-color is one knob doing two jobs. The built-in slider takes its fill from the tile's colour — which this section has already spent on encoding the phase — and a tile's color accepts no template, so "tint it by the current value" isn't expressible there at all. FLARE's feature paints its own track and never reads --feature-color, so both things can be true at once: the icon keeps the phase colour, the track carries the temperature.

The colour comes from the same Kelvin-to-RGB conversion the curve card draws with, so the bar and the curve directly above it in the same section agree by construction.

The unfilled part of the track still takes the tile's own colour, exactly as the built-in slider does — so a Curve row still reads as its phase at a glance, with the phase colour behind and the temperature in front. Everything about the control except that one fill colour is Home Assistant's, which is deliberate: it means there's no separate slider implementation here to drift out of step with the one sitting next to it in the same row.

It ships inside the integration and registers itself exactly as the curve card does, so there's still nothing extra to install. It's also not FLARE-specific: it's offered in the tile card editor for any number entity measured in K.

The section heading carries four badges reading straight off the schedule sensor: the current phase, and the brightness and colour temperature it's asking for right now (via state_content, which takes an attribute name). The fourth is the manual phase override, given a visibility condition of state_not: Auto so it only appears while an override is actually engaged — it reads "Auto" the vast majority of the time, which is noise on a header whose job is to show what's happening.

Repeat per schedule

One section per schedule sensor — drop each one into its own sections view column, or stack several in the same column if you'd rather. Nothing here reads a live sensor's actual values; it only builds entity IDs from the slug you give it, so it works whether or not that schedule exists yet.
